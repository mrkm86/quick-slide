# 実測で長いテストを先に開始する

## 判断

2 並列以上では、モジュールの実測時間が長い順にワーカーへ投入する。4 並列が既定であること、モジュール内のケースの順序、検証範囲、隔離方法は変えない。直列の `-j 1` は discovery の順序を保つ。

見積もりは `tests/durations.json` に置く。初期値は編集試験を分割した後の全件 4 並列の測定で得た秒数。同じ秒数のモジュールは発見順を保つ。未測定のモジュールも省かず、測定済みの後に発見順で実行する。なくなったモジュールの記録は実行対象に加えない。

このファイルは読み取り専用の実行順の参考値とし、テスト実行でリポジトリへ時間の記録を書き戻さない。更新時は全件実行の出力から新しい測定を確認する。数値は実行環境によって変わるため、制限時間や合否の判断には使わない。

## 理由と却下した案

分割後も最後に約 77 秒のバージョン固定試験が残った。長い試験を早く開始すれば短い試験と重なり、最後にワーカーが余る時間を減らせる。

バージョン固定試験だけを特別扱いする案は、ほかの長い試験にも同じ改善が効くため採らない。ケース数の多い順は所要時間と一致しないため採らない。実行のたびに全件を余分に走らせて測定する案は、短縮の目的に合わないため採らない。

## 検証

4 並列の全件実行は約 280 秒から約 245 秒になった（約 12% 短縮）。実行順の検証を 2 件追加した全 579 件が失敗なし、既存の skip は 5 件のまま。バージョン固定試験は最後ではなく開始直後に投入され、約 82 秒で完了した。ランナーの検証では、長いモジュールが最初に起動すること、同じ時間のときの順序、未測定モジュール、重複 ID を含むグループの保持を確認した。
