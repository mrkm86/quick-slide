# 0026: 停止時は HTTP 要求を待ってから接続を閉じる

## 状態

採用（Issue #16）

## 背景

HTTP 接続スレッドは daemon で動くため、`server_close()` は処理中の要求を待たない。
共有する SQLite 接続の `close()` と要求の `execute()` が競合すると、Python 自体が落ちることがある。

## 決定

`dispatch()` の入口と出口で、Condition の下で実行中の要求数を管理する。
`close()` は同じ Condition の下で受付を止め、要求数が 0 になるまで待つ。
その後にワーカー、HTTP 待ち受け、Store を閉じる。
要求の失敗や応答の失敗でも `finally` で要求数を戻す。
停止開始後の要求は DB に触れず、接続を閉じる 503 応答を返す。

HTTP 接続スレッドは daemon のままにする。keep-alive の次の要求待ちや、まだ要求行を
送っていない接続は DB に触れないため、停止時に待つ対象に含めない。
受付済みの要求には安全な DB 操作の完了が必要なので、待機に時間制限は設けない。
期限を超えて接続を閉じると元の競合が再発する。本文や応答の通信待ちは既存のソケットタイムアウトに従う。

## 採らなかった案

- `daemon_threads = False`: 接続スレッド全体を待つため、keep-alive や要求行の読み待ちまで停止を遅らせる。
- `store_lock` だけで `Store.close()` を囲む: 既に受付済みの要求が閉じた Store を使う可能性は残る。
- SQLite 接続の全面的なラッパー化: カーソルの読み出しやトランザクションも含めた排他が必要になる。
  今回の HTTP の寿命と接続の寿命の逆転は、受付と終了の境界で解消する。

## 検証

イベントで DB 操作前に複数の HTTP 要求を待たせ、停止中も接続が開いていること、
後続要求が 503 になること、先行要求が完了してから Store が閉じることを検証する。
既存の keep-alive 接続から届く停止後の要求も検証する。
