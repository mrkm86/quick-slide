# 0027 起動確認を待ちきれなかった子は、終了させてから失敗を返す

## 採用

`quick_slide.server start` の既定の待ちは30秒とする。停止・状態確認は10秒のまま、
明示した `--timeout` はどのコマンドでも優先する。会話の入口の起動待ちも既に30秒である。

起動を確認できなかったときは、その `start` が起こした子を組ごと止め、子の終了を待ってから
`start_failed` を返す。`child_exit_code` は終了後の値とする。先に起きていた別のサーバには触れない。
起動途中は `server.json` がまだ無い場合もあるため、停止には控えの PID ではなく起こした子を使う。

再起動の実プロセス試験は、起動結果の `ok` を確かめてから先へ進む。失敗時には `server.out` と
`server.log` の末尾を出す。後片付けは停止結果を確認し、応答できないサーバは強制終了して終了を待つ。

画面試験の Chrome も、起動確認の時間切れ・早期終了時は、コンストラクタの中でプロセスと
プロフィールを回収する。呼び側が `close` を登録する前の失敗を扱うためである。起動待ちは60秒とし、
失敗時に stderr の末尾を出す。Windows CI では最初の Chrome が30秒以内に起きない例があった。

ブラウザ試験で開いたタブは前面にし、CDP でも表示領域の寸法を明示する（`--window-size` は OS の窓の寸法）。モーションの実クリック試験は、CDP で iframe 内の要素の
実際の矩形を読み、描画と押下の到着を確認してからボタンを離す。外枠が ready になった直後も、中の
舞台が `scale(0)` のままの瞬間がローカルで観測された。外枠の幅から座標を推定するだけでは、Windows の
最初のクリックで部品ではなく舞台が押された。クリックの再送・検証の省略はしない。アプリの sandbox は変更しない。

Windows CI は「混みに弱い組」が失敗したら、その段の標準出力・標準エラーを artifact に保存する。
ジョブ全体の完了を待たずに失敗理由を取得し、後続の試験は今までどおり続ける。

## 理由

Windows CI では10秒で起動を確認できず、あとから起動したサーバが試験の置き場をつかんだまま残る
失敗が起きた（#19）。待ちを増やすだけでは、再び上限に達したときの置き去りを防げない。

## 却下

待ち時間だけを延ばす: 起動がさらに遅い場合や起動途中で止まった場合に子が残る。

子を残して失敗を返す: 呼び出し側が失敗後にやり直したり置き場を片付けたりする時点で、状態が確定しない。
