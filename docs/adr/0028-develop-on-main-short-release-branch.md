# 0028 開発は main に向け、リリースのブランチは版の番号を変えるだけにする

- 日付: 2026-10-16
- 状態: 採用
- 関係: `docs/RELEASING.md`・`docs/adr/0020-release-and-update-notice.md`

## 背景

1.0.1 では、リリースの PR（`release/1.0.1` → main）を開いたまま、そこへ直しを積んだ（停止時の競合・稼働時間の試験）。
同じ間に、別の直し（起動確認の時間切れ）は main に入った。開発の行き先が 2 つに分かれ、同じ試験を両方で別々に直して
衝突し、ADR の番号も重なった。main を release ブランチへ取り込む PR を挟んで、そろえ直した。

作業は Orca などで並行して進めるので、「どのブランチから切って、どこへ向けるか」を作業ごとに考えると間違える。

## 採用

- **ふだんの開発・修正は、main から切って main へ向ける。** 行き先は 1 か所だけにする
- **リリースのブランチ（`release/x.y.z`）は、出すと決めたときに main から切る。** 変えるのは版の置き場と `CHANGELOG.md` だけ
  （`tools/release.py prepare`）。開いている時間を短くし、入れたらすぐタグと GitHub Release まで進める
- **リリースの PR の間に直しが見つかったら、直しは main へ入れる。** release ブランチには main を取り込む（または main から
  切り直して `prepare` をやり直す）。release ブランチの上で直さない
- **出したら必ずタグ `v<バージョン>` を打つ。** 版のブランチを長く持たない。過去の版を直す必要が出たときだけ、タグから切る

### main に次の版の変更があるときの急ぎの直し

main に、まだ出していない変更（次の版に入れるもの）があって、それより先に直しだけを出したいとき:

1. タグから切る: `git switch -c release/1.0.2 v1.0.1`
2. 直しだけを入れる。main に先に入れて `git cherry-pick` で持ってくる
3. 版を上げてタグと GitHub Release まで進める（番号は出した順に付ける。次の番号を使ってよい）
4. CHANGELOG の新しい節が main にも入っていることを確かめる。main に溜まっていた変更は、その次の版として出す

番号は SemVer の形だけを使う。`1.0.1a` のような形は使わない。`-rc.1` などのハイフン付きは「試しに出す」ための番号で、
お知らせが出ない（ADR 0020）。

## 前提: main は、いつ持っていかれても動く状態に保つ

- `git clone` は既定のブランチ（main）の先頭を取る。マーケットプレイスの定義（`.claude-plugin/marketplace.json`・
  `.agents/plugins/marketplace.json`）もリポジトリの丸ごとを指していて、タグを指定していない。新しく入れる利用者も、
  main の先頭を受け取る
- タグと GitHub Release は、お知らせ（「新しいバージョンがあります」）の区切りに使う（ADR 0020）。中身の配り先は main
- なので、main に入れる PR は、出していない変更を含んでいても、それだけで壊れない状態にする。
  main の版の番号（`__version__`）は、出すまで前の版のままになる。中身と番号がずれる時期があることは受け入れる

## 却下した案

- **次の版のブランチ（`release/1.0.2` など）を先に切って、そこで開発する**: 開発の行き先が main と 2 つになり、1.0.1 と同じ
  間違いが起きる。版のブランチの上でも、手元の写しが古くなる問題（Orca がブランチを消せない）は変わらない
- **リリースの PR の上で直しを積む**（1.0.1 のやり方）: 上の背景のとおり、main と行き先が分かれる
- **長く持つ開発用のブランチ（develop など）を置く**: 一人と複数のエージェントで並行する規模では、合流の手間のほうが大きい

## 残っていること

- マーケットプレイスの定義でタグを指定すれば、新しく入れる利用者に出した版だけを配れる。ただし、版ごとに main の定義を
  書き換える手間と、更新の流れ（ADR 0020 の `claude plugin update`・`codex plugin add`）への影響を確かめていない。
  出していない変更が利用者に届いて困ることが起きたら、改めて決める
