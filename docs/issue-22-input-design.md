# 指示とローカル素材を持ち込む入口（Issue #22・設計案）

状態: 相談中。実装や採用を確定した ADR ではない。

**現在の GUI・保存形式・共通の指示生成・本番接続の設計は
[`design-template-contract.md`](design-template-contract.md) を参照。**
以下は議論の経緯を残す初期案であり、タブ内だけの保存や個別画像の登録を前提にした箇所は更新されている。

Issue の分担:
- [#22 デザインテンプレート（IMAGE / HTML）](https://github.com/mrkm86/quick-slide/issues/22)
- [#27 ブループリント（初期案は HTML）](https://github.com/mrkm86/quick-slide/issues/27)
- [#28 Motion の概要設計とロードマップ](https://github.com/mrkm86/quick-slide/issues/28)

## 目的

会話で image-slide に直接頼むときのように、原稿に加えて、台本の作り方・描き方・参照画像を
Quick Slide に渡せるようにする。ブランドやキャラクターの管理機能を先に増やすのではなく、
呼ぶ側が用意した指示とファイルを受け取り、台本係とエンジンへ届ける。

利用者は「この指示書に沿って、このキャラクターの絵を使って」と頼めばよく、
ブランドやスタイルを事前登録する必要はない。

## 現状から分かったこと

- 会話側のエージェントと、サーバ内で呼ぶ台本係は別の実行。会話の知識は自動で引き継がれない。
- `writer/prompt.py` は原稿内の指示に従うこと、ファイルを読むこと、`_characters`・`_layout` を禁じる。
- `writer/backends.py` は Claude の道具を無効にする。Codex も読み取り用の環境で呼び、
  プロンプトではファイルを読ませない。パスを文章に書くだけでは、両者に共通の入力契約にならない。
- `request` は原稿と別の利用者指示として渡せるが、下調べから始める経路であり、
  投入 API は `manuscript` と `request` の併用を受けない。
- `style_note` は既存の補足の入口だが、既定 400 字。指示書や素材一覧の代わりには狭い。
- image-slide はカスタムスタイル YAML、`--ref`、`--layout`、台本の `_characters` を受ける。
  サーバはこれらをそのまま使える入口を持たない。
- 版への復帰は既存成果物を再利用する仕組みがある。旧版の表示と、旧版の条件による再生成は区別する。

## 提案する入力

CLI の名前と形式は仮。まず用途を分け、オプション数は実装前に決める。

| 入力 | 内容 | 届け先 |
|---|---|---|
| 原稿 | 発表に使う事実・文章・材料 | 台本係 |
| 自由な指示書 | 構成、語り口、キャラクターの登場方針、素材の使い方 | 台本係 |
| カスタムスタイル | image-slide の既存 YAML。画風・余白など | 描き係。登場方針などは台本係にも共有 |
| 素材一覧 | 参照画像、キャラクター画像、構図のファイルと、その用途の説明 | 台本係には一覧、描き係には必要なファイル |

指示書の文を台本係が理解する余地を残す。「考え中のページではこのキャラクターを使う」などを
新しい真偽値オプションへ置き換える必要はない。
一方、画像の正確な選択には、名前とファイルを結ぶ小さな素材一覧が要る。

たとえば `--instructions-file brief.md` と `--materials-file materials.yaml` を受け、
素材一覧から既存のスタイル YAML や画像を参照する形が考えられる。
指示書・素材一覧・画像の中身は未実装であり、この例は CLI の確定仕様ではない。

## 入力から描画まで

1. 会話側は、利用者が指定した指示書と素材を整えて入口へ渡す。
2. CLI は指定ファイルを読み、素材一覧に書いた相対パスをその一覧のディレクトリ基準で解決する。
   本文中のパスを自動探索したり、指示書から無制限に別ファイルをたどったりはしない。
3. サーバは受け取った文とファイルを取り込み、画像は既存の assets を利用して内容のハッシュで保持する。
   原本を次の描画時に読み直す方式にはしない。具体的な置き場は既存のパス管理を通す。
4. 台本係へ、原稿とは別に利用者の指示書と、使用可能な素材の名前・説明を渡す。
   原稿や参考資料を自動的に利用者指示へ昇格させない。
5. 台本係は内容から登場ページとポーズを決め、素材 ID を参照した台本を返す。
   必要なら、素材の説明だけで足りるか、画像も見せるべきかを後で検証する。
6. サーバが素材 ID の存在を検査し、エンジン用台本では保存済みファイルへのパスに置き換える。
   キャラクターは image-slide の既存の `{name, image, pose}` に変換する。
7. カスタムスタイル・構図・参照画像は、エンジン既存の入力へ渡す。
   エンジンに渡す検査と描画の両方で同じ入力を使う。

キャラクターの `pose` はエンジンでは自由な描画指示の文字列。
登録済みポーズの選択だけに制限する必要はない。同じ参照画像から、文で表情や動きを指示できる。
ポーズ別の画像がある場合は、台本係が合う画像を選べばよい。

## 指示の届け方と衝突

- 台本の構成や登場ページの指示は台本係へ渡す。カスタムスタイルだけに書いても、
  そこから台本の構成が自動で変わるわけではない。
- 描画の制約は描き係にも届ける。台本係に伝えるだけでは画風や余白は保証できない。
- 指示書の全文を台本係と描き係の双方に渡すか、描画用の節を明示して渡すかは未決。
  自動要約で意図を落とす方式は初期案にしない。
- ブランドの配色と指示書の色指定、既存 CLI の明示値と持ち込みファイルの指定が
  食い違うときの優先順位は、実装前に合意する。黙って片方を捨てない。
- 非対応モードの入力、存在しない素材、参照画像の上限超過は検査で示す。
  上限は構図の見本も含めてエンジンと一致させ、台本で解決できる問題は既存の書き直しへ返す。

## 修正と版

- 指示と素材はデッキに引き継ぐ。毎回添付し直さなくてよい。
- ページ修正の台本係にも、継続中の指示・使用可能な素材・現在のキャラクター指定を見せる。
  キャラクター指定を省略したときの継承と、明示的に消すときの空配列を区別する案を検討する。
- 指示書や素材を差し替える場合は新しい入力の版にし、描いた回は使用した入力の版を参照する。
  仕事の実行中に内容が入れ替わらないよう、回の開始時点で固定する。
- 既存の「版に戻す」は成果物を使う。旧版の条件で描き直す機能まで含めるかは別途決める。
  後者に備えて、少なくとも各回が使った文・素材・スタイルの内容をたどれるようにする。
- 素材の参照と削除は、既存の資産管理・ゴミ箱の扱いに合わせて確認する。
- 指示書の本文は原稿・依頼文と同じ配慮で保存し、ログやイベント、投入要約へ全文を複写しない。
  入力の同一判定には、指示とファイルの内容も含める。

## 最初に確かめる範囲

登録画面や共通キャラクター DB は作らず、まずピッチで次を検証する案。

1. 原稿と自由な指示書を併用し、台本の構成や語り口に反映される。
2. 既存のカスタムスタイル YAML とキャラクター画像を持ち込める。
3. 内容に合わせて登場するページ・登場しないページ・ポーズを台本係が選べる。
4. 画面から文字を修正しても、渡した指示と素材が使える。
5. 元ファイルを移動・変更しても、取り込んだ素材で描画を続けられる。
6. 旧版への復帰は既存の成果物を使い、入力の履歴も失わない。

全ページ共通の参照画像とカスタム構図も入力の設計対象に含めるが、最初の実装範囲に含めるかは未決。
実際の生成品質は CLI を模したテストだけでは判定できないため、実描画で確認する段を別に設ける。

## 用語の整理: デザインテンプレートとブループリント

会話での整理に基づき、エンジン別ではなく「作るときに何を固定するか」で区別する。

- **デザインテンプレート**: 資料を作る方針。会議用フォーマットなど、構成・画風・素材の使い方を持つ。
  image-slide と html-slide のどちらにもありえる。
- **ブループリント**: 押印するように元の資料を再利用し、氏名欄のような指定部分だけを書き換えるもの。
  元の資料と書き換え可能な範囲を持つ。

| 概念 | 固定するもの | AI に任せるもの |
|---|---|---|
| デザインテンプレート | 指示・画風・素材・構成の方針 | 台本とページの生成 |
| ブループリント | 元デッキの指定版・固定ページ・固定部分 | 指定された差し替え部分と追加ページ |

前者は image-slide だけでなく html-slide でも使える。後者も本質的にはエンジンではなく、
完成した資料の一部を保持する作成方式。登録・選択・指示・素材・版の共通部分は共有し、
元デッキと変更可能範囲の指定は、ブループリントを使う方式に追加する。

ブループリントには、変更を許すページ・文字の枠・追加ページの挿入位置を明示する。
「顧客に合わせる」といった文章だけで固定部分の保持を保証しない。
初期案では指定のない範囲は変更不可とし、AI の結果も適用時に範囲を検査する。
文字の枠への差し替えと、可変ページ全体の生成は別の操作として扱う。
固定部分の一致と、可変部分の文字のはみ出しをそれぞれ確認する。

利用ごとに元デッキの指定版から独立したデッキを作る。
前回の出力を次の案件の土台にすると、前回だけの内容が残るため。
元の記載を消す必要がある可変部分は、今回の材料が無いときの扱いも定義する。
ページの選択・省略・順序変更は資料の組み立てとして扱い、ページ内部の文字の差し替えとは区別する。

現在は取り込んだ HTML の文字を番号で指定して置換できるが、番号はその版に対するもの。
ブループリントの項目名と枠の対応には、元の版を固定するか、安定した枠 ID を導入する設計が要る。
同じ文字列の一括置換だけで宛先や本文を特定する方式にはしない。

ブランドは色・ロゴ・字体の共通設定、デザインテンプレートは作成方針、ブループリントは書き換え範囲を持つ土台として区別する。
取り込み済み資料は元の書式・ロゴを持つため、ブランド変更で自動的に全体が変わるとは扱わない。
画面ではブランドから関連するデザインテンプレートやブループリントを選べても、内部で同一の設定にまとめる必要はない。

この方式は Issue #22 の自由な入力と共通部分を持つが、差し替え範囲の指定・適用・検査は追加の設計対象。
自由な入力の対応だけで実現したことにはしない。

## モードの範囲とロードマップ

初期対応は IMAGE（pitch）と HTML（presentation）の 2 モードを提案する。
共通の入力形式には対応モードを持たせ、Motion 向けに使えない入力は生成開始前に理由を示して断る。
image-slide のスタイル YAML や参照画像の意味を、Motion へそのまま流用しない。

| 段 | 対象 | 到達点 |
|---|---|---|
| 1 | IMAGE / HTML のデザインテンプレート入力 | 指示・素材のファイル取り込み、回への保存、初稿と修正への継承 |
| 2 | デザインテンプレートの登録・選択 | 段1と同じ内容を保存して呼び出す。利用者はファイルを自作しなくてよい |
| 3 | HTML のブループリント | 元の指定版から新しいデッキを作り、指定された欄だけを差し替える |
| 4 | Motion のデザインテンプレート | 場面構成、拍の進め方、共通造形、動きの方針を再利用する |
| 5 | Motion のブループリント | 完成した場面・演出を保持し、指定した文字や値を差し替える |

段3と段4は段1・2の共通部分が整えば独立に進められる。番号は着手日の確約ではない。
IMAGE のブループリントは初期対象外。画像に焼かれた文字の置換では固定部分の保持を保証できず、
対応する場合は背景と差し替え部品を分けるなど別の設計が必要になる。

### Motion のデザインテンプレート

現行の台本係は、全体の構成・共通設計を作り、各場面を分けて実装する。
共通設計にはレイアウト・字体・造形・動きの方針があり、デザインテンプレートを渡す先として使える。
利用者の指示を構成係と各場面係の両方へ渡し、修正時も引き継ぐ。

保存対象の例は「結論から始める」「1場面で1つの概念を扱う」「クリックごとに比較対象を増やす」
「共通の図形と配置を使う」。秒数だけの動画テンプレートとして扱わず、現在の場面・拍・発表操作に合わせる。
画像生成の画風や `_characters` と同じ仕組みで動くキャラクターまで実現したとは扱わない。

### Motion のブループリント

元の台本の指定版を保存し、安定した項目 ID で文字・数値などの差し替え範囲を指定する案。
場面の ID・拍・アニメーション・要素参照・共通部品は、初期案では変更不可とする。
差し替えた内容が全拍で表示できるか、はみ出さないかを現行の Motion 検査に加えて確認する。
値が図形の大きさや演出にも影響する場合は、宣言した連動部分も更新するか、対応外として止める。
全文の文字列置換だけでは実装しない。場面の追加や拍の変更は将来の別段階とする。

初期の 2 モード対応で Motion の実装まで含める必要はないが、登録する入力の版・対応モード・素材参照は
後から Motion でも使える共通部分として設計する。実装時の詳細は各 Issue で決める。

## 設定画面のプレビュー

（この画面案は、本番の設定画面ができた時点でリポジトリから外した。以下は経緯。）
`web/app/settings-preview.html` は、既存の設定トップ・共通 CSS・DOM 部品を使った操作可能な画面案。
通常のアプリ起動には接続せず、架空のデータだけで表示する。実データの API・生成処理は呼ばない。
`python3 tools/preview_settings.py` で起動する専用サーバが、架空の目録と保存しない配色計算だけを返す。
ブランド一覧・詳細は既存の `SS.views.settings` をそのまま呼ぶ。ブランド詳細を別の見た目に作り直さない。

| 入口 | 画面と操作 |
|---|---|
| 設定 → ブランド → 対象ブランド | 既存の色・ロゴ・フッター・ウォーターマーク・右側プレビューを保持し、下部にデザインテンプレートの一覧と追加・編集を足す |
| ブランド詳細内のデザインテンプレート欄 | 会議用・ピッチ用を既存の行の見た目で並べ、追加・編集する。タブや独立したカード一覧へ置き換えない |
| デザインテンプレート編集 | 基本・構成・追加指示・リソースの4タブで設定する（詳細は契約の文書） |
| 設定 → ブループリント | ブランドを選ばず、独立した資料の一覧を見る |
| ブループリント登録・設定 | 元資料の版を指定し、固定部分と差し替え欄を決める |
| ページの選択 | 複数のブループリントからページを選び、作る資料の順番を調整する |
| 指定欄の確認 | 選択ページの差し替え可能な欄だけを入力する |
| 組み立て結果 | ページの順序・出所・差し替え内容の模式図を見る |

デザインテンプレートの右側は、ブランドの継承内容と作成方針を確かめる見本の置き場。
プレビューでは固定の模式図を使い、指示から生成した結果とは表示しない。
本実装での試作生成の有無と、その操作・待ち時間は別途決める。

ブループリントは「登録する人」と「使う人」の操作を分ける。
登録時に編集範囲を定義し、使うときにはその範囲だけを入力欄として見せる。
画面案の登録操作は元資料の選択と差し替え欄の例まで。実際の枠の選択、必須・未入力時の扱い、
登録内容の永続保存は実装していない。

テンプレートの編集と既存ブループリントの設定は、このタブ内の状態へ保存して再表示できる。
再読み込みで初期状態に戻る。添付はファイル名の表示だけで、内容を読んだりアップロードしたりしない。
資料の書き出し、AI による文章作成、Motion はこの画面案には含めない。

既存設定と実際の指示書を対応付けて試す場合は、`tools/preview_settings.py --data-dir <検証用フォルダ>`
で外部の `bundle.json` と取り込み済み素材を読む。目録・テンプレート・参照ファイルを分離し、
検証用フォルダはリポジトリの外に限定する。
スマホなどほかの端末から見るときは、`--host <私設網でのこのパソコンのアドレス> --allow-host <その網での名前>` で起動する。
すべてのアドレス（`0.0.0.0`）では待ち受けない。許可していない Host の要求は断り、パスを選ぶダイアログは
このパソコン自身からの操作でだけ開く（ダイアログはサーバの画面に出るため）。ブランド名や指示の本文をプレビューのコードへ埋め込まない。
ファイルの添付は検証用フォルダへ取り込み、ローカルの写しを表示する。
元の指示との対応表のような説明は設定画面に載せない（設定上の効力がなく、利用者が編集できないため）。
