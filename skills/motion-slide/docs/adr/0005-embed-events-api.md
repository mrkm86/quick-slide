# 0005. 埋め込み用イベント API v1

- **日付**: 2026-11-04
- **状態**: 実装済み・動作確認済み（`tests/embed_check.py`・`check.py` の埋め込み検査。HTML の増分は 2,024 バイト）

## 背景と範囲

HTML 1 枚の発表画面を `sandbox="allow-scripts"` の iframe に置くと、親ページは内部の拍を直接読めない。画面が現在位置を親へ通知し、親から画面移動を指示できる、中立の `postMessage` 仕様を定める。親ページでの通知の使い道は本仕様に含めない。

既存エンジンは `go`・`next`・`prev` から `apply()` に入り、`S` と `B` が現在の場面と拍を示す。`build.py` は `engine.js` と `engine.css` を HTML にそのまま埋め込む。この経路を使い、台本には通信処理を書かない。

## 決めたこと

### 単位、番号、互換性、配布

1. **拍を通しの既定単位にする。** `index` と `total` で拍を表し、`scene` と `beat` も送る。変化が起きる最小単位が拍であり、場面ごとの拍数が異なっても `index` は連続する。親ページは必要なら `scene` だけを見て場面単位にまとめられる。
2. **API の位置はすべて 0 始まりにする。** `scene` は場面の通し番号、`beat` はその場面内の番号、`index` は全場面を通した拍番号。既存の内部状態と台本の拍指定に一致する。画面上の `1 / N` 表示と既存のハッシュ表記は変えない。
3. **既存の出力 HTML はそのまま使える。** 新 API を使うには新しいエンジンで HTML を組み直す。古い HTML は発信せず、親ページは通知が来ない場合を扱う。既存ファイルへの後付け処理や自動移行はしない。
4. **他形式向けのスニペットは配らない。** v1 は拍を持つこのエンジンの仕様として公開し、親ページが受け取る形だけを文書化する。他形式では「場面」と「拍」の対応が異なり、数行の部品では意味をそろえられない。共通化の要望が具体化した時点で別に設計する。

### メッセージの形と発信条件

メッセージは文字列化せず、構造化複製できる平坦なオブジェクトにする。共通の `namespace` は `"motion-slide"`、`version` は数値の `1`。値は固定の名前と数値だけに限り、題・本文・場面 ID・個人情報・現在位置の文字列などを含めない。発信先は `window.parent.postMessage(message, '*')`。不透明なオリジンの iframe から親のオリジンを決められないため `*` とし、`window.parent === window` なら発信しない。親ページは受信時に `event.source` が対象 iframe の `contentWindow` と一致することを確かめる。

| 方向 | 形 | 発生条件 |
|---|---|---|
| 画面 → 親 | `{namespace, version, type:"ready", scenes, beats}` | 初期表示の準備が済んだとき、および有効な `request-state` を受けたとき。`scenes` は場面数、`beats` は総拍数 |
| 画面 → 親 | `{namespace, version, type:"change", scene, beat, index, total}` | 初期表示と、位置が実際に変わったとき。戻る・自動再生・一覧からの移動も含む。`total === beats` |
| 画面 → 親 | `{namespace, version, type:"end", total}` | 最後の拍に**入った**とき。初期位置が最後の拍の場合も含む。いったん離れて再び入れば再発信する |
| 親 → 画面 | `{namespace, version, type:"command", name:"next"}` | 1 拍進める |
| 親 → 画面 | `{namespace, version, type:"command", name:"prev"}` | 1 拍戻す |
| 親 → 画面 | `{namespace, version, type:"command", name:"goto", index}` | 通しの拍番号へ移る |
| 親 → 画面 | `{namespace, version, type:"request-state"}` | 現在の全体数と位置を問い合わせる |

初期表示の順序は `ready` → `change` →（最後の拍なら）`end`。`request-state` への返答は `ready` → 現在位置の `change` とし、位置を移さず、`end` は再発信しない。`next` を最後の拍で押す、`prev` を先頭で押す、同じ `index` へ `goto` する、同じ拍を描き直す場合は `change`・`end` を重ねない。`end` は末尾に入ったという出来事であり、再生タイマーの終了を意味しない。

受信側は初期化後にだけ動作し、`event.source === window.parent`、`data` が配列でも null でもないオブジェクト、`namespace` の完全一致、`version === 1`、既知の `type` と `name` を確認する。`goto.index` は `Number.isInteger(index)` かつ `0 <= index < total` を必須とし、数値への暗黙変換や範囲への丸めをしない。不正なメッセージは例外や応答を出さず無視する。命令は既存の `next`・`prev`・`go` に渡し、新たな外部通信、保存、移動先の変更を起こさない。親のオリジンが `null` でも成立するよう `event.origin` で許可判定しない。

HTML の増分は埋め込まれる `engine.js` の増分だけ。実装予算は発信と番号計算に約 900 バイト、受信と検証に約 650 バイト、初期化・遷移への接続に約 250 バイト、計 **約 1,800 バイト**（UTF-8 の原文、圧縮前）とする。実装時は同じ台本を変更前後の `build.py --no-thumbs --logo none` で組み、出力 HTML のバイト差が **2,048 バイト以下**であることを測る。予算を超える場合は機能を削らず設計を再検討する。

### 検証と受け入れ基準

`tests/` の既存の `run.sh` と一時フォルダ、ローカルのブラウザ試験の流儀に合わせ、組み立てた HTML を `sandbox="allow-scripts"`（`allow-same-origin` なし）の iframe に入れる。親ページのテスト用 `message` リスナーは対象 iframe の `event.source` と仕様 v1 を確認する。読み込み直後の `ready` → `change`、全拍を順に送ったときの位置列と一度の `end`、`prev` と `goto` で戻った位置、再度末尾へ入ったときの `end` を検証する。`request-state` は現在位置を返すが移動しないことも確かめる。

別 namespace・版・型・命令名、非オブジェクト、別フレームの送信、`goto.index` の小数・文字列・負数・総拍数以上・欠落を送って状態と通知数が変わらないことを確かめる。単独表示ではメッセージ発信処理が働かず、既存のキー・クリック・自動再生・一覧・音・見た目と HTML サイズを回帰確認する。検査は外部取得に依存せず、通信のために storage・`location`・`history` を使わないことをコードで確認する。既存の位置ハッシュ処理はこの API では変更しない。

### 公開仕様の前例

公開されているプレゼン用エンジンの公式「postMessage API」「Events」資料を確認した。iframe 内の画面から親へ変化イベントを伝え、親から画面移動を指示する構成、起動時と位置変更時を区別する考え方は共通する。一方、その仕様には文字列化したメッセージや広いメソッド呼び出しもある。ここでは拍と場面の 2 階層、版の固定、受信命令の限定が必要なため、メッセージの名前や形は独立させる。

## 採らなかった案と理由

| 案 | 理由 |
|---|---|
| 場面だけを既定の位置として送る | 場面内の拍の変化を見失う |
| 1 始まりの番号を API に使う | 内部状態と変換が必要になり、`goto` の境界を誤りやすい |
| 既存 HTML に通信コードを後付けする | 出力ごとに改変が必要で、組み立て結果と一致しなくなる |
| 他形式用スニペットを同時に配る | 拍のない形式で同じフィールドをどう定義するか決まっていない |
| 親の任意メソッド呼び出しを許す | 公開する操作面が広がり、検証と互換性維持が難しい |
| 発信に現在位置の文字列や台本の内容を含める | 位置を示す整数で足り、不要な情報が親に渡る |
| 終端を最後の拍からさらに進めた時だけ発信する | 最後の拍に着いた事実が直ちに伝わらず、初期位置が末尾の場合も扱えない |

## 未決事項

なし。実装時の iframe 試験で既存のハッシュ処理が例外になる環境が見つかった場合は、その処理を例外から守る案とハッシュ更新を行わない案を比較し、単独表示への影響が小さい前者を推奨する。この API の通信経路へ位置情報の読み書きを足す判断はしない。
