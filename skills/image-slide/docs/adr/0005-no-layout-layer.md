# 0005 レイアウトの層をやめ、構図は Codex に任せる（作風の既定はピッチ寄り）

- 日付: 2026-10-05
- 状態: 採用（[0004](0004-layout-layer.md) を置き換える）
- 問い: 0004 でレイアウトの層（15種）を入れたが、印象的なピッチスライドには、指定しすぎないほうがよいのではないか。3通りを描いて比べ、レイアウトの層をやめて構図は Codex に任せることにした

## 比べたこと（2026-10-04・見本の5枚・本物の Codex・各1回）

| | 構図の指定 | 作風 | 結果 |
|---|---|---|---|
| ① | 型ごとの既定のレイアウトを渡す | 業務資料寄り | イラストとアイコンの整った業務資料 |
| ② | 渡さない | 業務資料寄り | ①とほとんど同じ |
| ③ | 渡さない | ピッチ寄り | 表紙・2枚目・締めが写真調の全面ビジュアルになり、一番ピッチらしい |

- 構図を指定しても、しなくても、絵はほぼ同じ。印象を決めていたのは作風だった
- 棒グラフ・流れの図など、中身から形が決まるページは、構図を指定しなくても崩れなかった（コンテンツの種類の説明で「何を載せるか」を伝えているため）
- 各1回なので、①と②の小さな差は揺れの範囲かもしれない

## 決めたこと

1. **レイアウトの層を持たない。** `layouts/`（15種）・`layout-map.yaml`・`scripts/layouts.py`・入口の `layouts`・`--layout-mode`・`--auto-layout` を消した
2. 描く指示では構図を指定せず、「このページのコンテンツが一番印象に残り、一番よく伝わる構図を自由に決める」とだけ言う（`prompt.COMPOSITION`）
3. **作風の既定をピッチ寄りにする**（`--style-base pitch`）。業務資料寄りにしたいときは `--style-base business`
4. 見せ方の注文があるページは、台本の `_visual` に文章で書く（「写真を全面に敷いて」など）。見せ方が決まっている資料（週報・月報）は、ユーザーが自分のレイアウトを持ち込む（[0006](0006-bring-your-own-layout.md)）
5. html-slide 由来の配置の指定（`layout: left` など）は、台本を書いた人の意図として、これまでどおり描く指示に添える

## 理由

- 比べた結果、構図の指定は効き目が小さく、作風の効き目が大きかった
- パターンの棚を持つ生成器があるのは、台本にページの種類の欄が無く、パターンの注記がページの種類を伝える唯一の手がかりだから。image-slide はコンテンツの種類（`type`）がその役を担うので、レイアウトを重ねても足される情報が少ない
- 層を持つと、陳腐化したときに直す物が増える。使い道がはっきりしてから足せばよい（quick-slide v2 でピッチモードの見せ方を選ぶ画面を作るときなど）

## 却下した案

| 案 | 却下の理由 |
|---|---|
| 棚は残し、指定があるときだけ `_layout` で使う | 「写真を全面に」程度なら `_visual` の文章で足りる。使い道のはっきりしない層を持ち続けない |
| 型ごとの候補から Codex に選ばせる（`auto`） | 任せるなら候補を渡さなくてよい。比較でも候補を渡す効き目は見えなかった |
