# 0014 絵は Codex だけで描く（Azure OpenAI の API で描く道は試して見送った）

- 日付: 2026-10-07
- 状態: **見送り。** 一度入れたコードは同じ日に元に戻した。この ADR は試した記録として残す
- 前提: 組織・チーム向けには、個人契約の Codex より、Azure OpenAI などの API を会社の契約で呼ぶほうが使いやすい場合がある。
  そこで Azure 版の API で描く口を一度入れた（プロバイダーは設定で指定・参照画像は5枚まで・品質は low 固定）。
  品質が担保できないなら API はやめる前提で比べ、下の結果を見てコードを元に戻した
- html-slide の ADR 0013 も同じ（画像の枠を Azure で描く道を見送った）

## 決めたこと

1. **絵は Codex（ChatGPT のサブスク枠の gpt-image-2）だけで描く。** API で描く口（設定の `image_provider`・`providers.py`）は持たない
2. **同じ gpt-image-2 でも、呼び方で結果が変わった。** これがこの ADR でいちばん残したいこと
   - Azure の**同じデプロイ（`gpt-image-2`）**を、画像の口（`images/edits`）と会話の口（Responses API の画像生成の道具）の2通りで呼んだ。
     絵を描くモデルは同じなのに、キャラの取り違え・キャラの置き場所・返る絵の大きさが違った（下の「測ったこと」）
   - 会話の口では、会話のモデルが頼み文の頭に「参照画像1＝Hana…」と対応を書き足して渡していた。Codex もこの口で描いている見込みが高い
     （返る絵が 1672×941 で Codex とまったく同じ）。Codex の結果の良さは、絵のモデルではなく、この呼び方から来ていると見ている
   - だから、API で描く道をまた作るなら、画像の口ではなく会話の口で作る（会話のモデルのデプロイが要る・その分の料金がかかる）
3. 文字の崩れは品質（low・medium・high）で変わり、構図と帯のはみ出しは品質でも口でも変わらなかった。帯は、この週報のレイアウトが下まで詰まりすぎている方の問題と見ている

## 入れていたときの形（作り直すときの参考）

- 選ぶのは設定の `image_provider: codex | azure` の1行だけ。環境変数に鍵があるだけでは切り替えない（黙って従量課金に変わる罠を作らない）
- 接続先（endpoint・deployment・api_version）は設定、鍵は `api_key_file` が指すファイルの `AZURE_API_KEY=` の行。無ければ同じ名前の環境変数
- 品質は low 固定・参照画像は5枚まで。失敗の種類（rate・auth・refused など）を codex とそろえ、並列・待ち・描き直しの仕組みをそのまま使った
- 画像の口は大きさを「縦横とも16の倍数」で自由に指定できた（16:9 は 1920×1088）。会話の口は 1024×1024・1024×1536・1536×1024・auto だけ

## 測ったこと（2026-10-07・本物の Azure・計3枚）

| 何を | 結果 |
|---|---|
| 実際の週報の1枚（Codex 版と同じ指示・キャラ3人の参照画像 → edits） | 1回 42 秒。1回目は下端の帯に近況の段がはみ出して描き直し、2回目もはみ出して地の色の板を敷いた（2枚ぶんの料金）。Codex 版は4分1秒 |
| html-slide の縦長の枠（1:1.23・generations） | 1296×1600 で受けた。23.5 秒 |

- low でも見出し・本文の日本語はほぼ正しく描けた。絵の中の小さな文字（関所の札）は崩れた
- Codex 版と同じく、説明文に出た製品名から、製品のロゴが絵に描き込まれた（描く先の違いではない）
- Hana は見出しの横ではなく右に大きく立った。近況の段は Codex 版より下に寄り、帯を食った

### 品質を変えて描いた（同じ指示・描き直しなし・計4枚）

品質はこの試しの中だけ差し替えた（そのときのコードの既定は low）。

| | 時間 | 出力トークン | 帯 | 絵の中の小さな文字 | Pochi（黒ラブ） | 近況の欄の名前 |
|---|---|---|---|---|---|---|
| Codex（品質不明） | 133 秒 | — | 空いた（2回目） | 読める | 黒ラブ | あり |
| low | 42 秒 | 148 | はみ出し 18.9% | 崩れた | 黒ラブ | 無し |
| medium 1 | 59 秒 | 1,325 | 8.1% | 読める | 柴犬（取り違え） | 無し |
| medium 2 | 63 秒 | 1,325 | 17.8% | 読める | 黒柴（取り違え） | 無し |
| high 1 | 107 秒 | 5,300 | 2.7% | 読める | 黒ラブ | あり |
| high 2 | 103 秒 | 5,300 | 8.2% | 読める | 柴犬（取り違え） | 無し |

- **品質で変わるのは、文字と絵の細かさ。** low は絵の中の札の文字が崩れた。medium から読める。high は medium より少し締まるが、出力トークンは4倍・時間は1.7倍
- **品質で変わらないのは構図。** Azure の5枚はどれも、流れ図を縦4段に積み、Hana を大きく立たせ、近況の段が下端の帯にはみ出した
  （Codex 版は横4段の流れ図・Hana は見出しの横に小さく・帯は空いた）。差は品質ではなく、指示が直に届くか（Codex はエージェントが渡す）と、
  参照画像を edits（編集する元の絵）として渡すかの方にある、と見ている（1つずつ切り分けてはいない）
- キャラ3人の取り違え（Pochi が、もう1人の柴犬のキャラと同じ柴犬になる）は5枚中3枚。edits では「参照画像2は〜」の番号の対応が効きにくいらしい
- 説明文の製品名から製品のロゴが出るのは、品質によらない

### 会話の口（Responses API の画像生成の道具）を試した（low・2枚）

実装には入れず、試しの台本で描いた。
会話のモデルは Azure にある `gpt-5.4`（推論 low）、画像は `gpt-image-2`（`x-ms-oai-image-generation-deployment` ヘッダで指す）。

- **返る絵は 1672×941。Codex とまったく同じ大きさ。** Codex もこの口（大きさ auto）で描いていると見ている。この口は大きさを 1024×1024・1024×1536・1536×1024・auto からしか選べない
- **キャラの取り違えが消えた。** 2枚とも Pochi は黒ラブ（名札も参照画像のまま）、Hana は見出しの横で指を立てた。
  会話のモデルが頼み文の頭に「reference image 1 = Hana, reference image 2 = …, reference image 3 = Pochi」と足していた（revised_prompt）。
  Codex が「うまくやっていた」のはここだと見ている。指示文の本文は書き換えずにそのまま渡していた（約 5,600 字）
- **帯のはみ出しは残った**（16.4%・16.7%）。流れ図も縦4段。帯は Codex も1回目ははみ出しており、この週報の詰まった構図の問題が大きいと見ている
- low の崩れは小さな札の文字だけ（「今週の案件」のラベル・「承認者」）
- 1枚 72〜75 秒。会話のモデルの分の料金が足される（入力 約 12,900・出力 約 4,300 トークン。出力は指示文の写し）

## 理由

- 普段使いは Codex で、API は組織向けの備えだった。Codex より劣る絵になる口を抱えておく理由が無い
- 画像の口では、キャラの取り違えが5枚中3枚。会話の口なら Codex 並みになったが、それなら Codex と同じ呼び方を API で組み直すことになり、今は要らない
- 会社の契約で描く要件が出たら、上の「同じ gpt-image-2 でも呼び方で変わる」を前提に、会話の口で作る
