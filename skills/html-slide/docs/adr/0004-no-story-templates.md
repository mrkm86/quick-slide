# 0004 ストーリーテンプレート（旧: 構成の型）を持たない

- 日付: 2026-10-04
- 状態: 採用

3つのエンジン（html-slide・image-slide・html-video）の層を比べ、名前を整理する中で決めた。

## 層の名前（このとき決めた）

| 名前 | 何を決めるか | 台本の中では | 持ち主 |
|---|---|---|---|
| **ストーリー** | 資料全体の流れ。何をどの順で言うか・枚数 | 台本そのもの（`slides[]` の並びと、各ページの言葉・数字） | **使う側**（LLM が書く・呼ぶ側のスキル） |
| **コンテンツ** | 1枚に載せる中身の種類（主張・数字・比較・手順・表…）。旧称「ページの型」「画面の型」 | 各ページの `type`（23種） | エンジン共通の語彙（製品が持つ） |
| **レイアウト** | そのコンテンツをどう並べて見せるか | html-slide は型の中（座標・変化形）、image-slide は `_layout`（15種） | エンジンごと |

- 「フォーマット」はページの型の呼び名に使わない。quick-slide では C フォーマット（帯・ページ番号・差し込み値）の意味で使っている
- 「body」も使わない。台本のキー（補足文・説明文）とぶつかる
- 台本の JSON のキー（`type`・`_layout`）は変えない。名前は説明の言葉だけを変える

## 決めたこと

1. **エンジンはストーリーの型を持たない。** 構成の型10種（`outlines/`）・雛形を出す `scaffold`・章立ての警告（必須の章・順番・向かない型・同じ型の連続・最後が締めでない）を消した
2. ストーリーは**使う側が決める**。普通は台本を書く LLM に任せる（「XX について」と頼めば、枚数と流れは LLM が決められる）
3. **決まった流れが要る用途**（社内の稟議・部の定例のように、組織の決まりで順番や必須の章があるもの）は、**呼ぶ側のスキル**が流れを決め、検品をかけて確かめる。エンジンは渡された台本を描くだけ
4. 目安は1行だけ残す: `references/deck-format.md` の「書く前に」の 3.（筋は 結論 → 課題 → 原因 → 解決 → 効果 → 次の一手）。用途別の章立ては書かない（書くと型を持つのと変わらない）
5. 前の版の台本との互換: 一番外の `outline` と各ページの `role` は**受け取って読み飛ばす**（止めない・警告もしない）。image-slide も同じ台本を受けるので、一番外のキーの並びは変えない

## 理由

- ストーリーを作るのは LLM の得意なところで、型で縛るより、依頼と中身に合わせて LLM が決めるほうが良い流れになる見込み
- 型を製品が持つと、「こんな資料形式もいいよね」のたびに製品の改修が要る。一方で一般的な流れは、もう LLM が知っている
- LLM が知らないのは組織の決まりだけで、それは使う側の知識。エンジンに置く理由が無い
- 構成の型は html-slide を作るときに一緒に作ったが、html-slide に置いたのは置き場がほかに無かったからで、エンジンの機能だからではなかった

## 却下した案

| 案 | 却下の理由 |
|---|---|
| image-slide にも写す | 同じものが2か所にでき、そもそもエンジンが持つものではない |
| エンジンの外の独立した部品にする | 一度はこの案を勧めたが、型として持つこと自体が要らない（LLM に任せられる）と決まった |
| quick-slide v2 に持たせる | 同上。組織の決まりは、quick-slide v2 でも「利用者が保存しておく追加の指示」の1つとして持てば足りる |
| 10種を例として手引きに残す | 用途別の流れを書くと、結局それに引きずられる。目安は筋の1行に絞った |

## 消したもの（記録）

- `outlines/`（10種: proposal・pitch-internal・ringi・report・status・training・earnings・briefing・pitch・research）・`scripts/deck_outline.py`・`references/outlines.md`・入口の `scaffold`・`deck.py --scaffold`
- 型ごとの最小の中身（雛形用の `placeholder`）は、全部の型を試すテストが使うので `tests/test_deck.py` の `minimal` に移した
