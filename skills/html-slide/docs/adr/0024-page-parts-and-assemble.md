# 0024 ページごとの書き出しの部品と、混ぜた書き出しを組む `assemble`

- 日付: 2026-10-11
- 状態: 採用

## 決めたこと

呼ぶ側（Quick Slide）が、違う回で描いたページを混ぜた PPTX・PDF を作れるようにする。エンジンは状態を持たない
ままにし、部品を「出す」口と「並べて組む」口だけを足す。

1. **`deck --parts <JSON>`**（`revise` も同じ）: PPTX の部品 JSON（`extract.mjs` の出力。形は
   `references/parts-format.md`）をそのまま書き出す。画像の `src` は絶対パス（作業フォルダの `assets/` など）。
   ページごとに分けて画像を控えるのは呼ぶ側の仕事（エンジンは回を知らない）
2. **`assemble --manifest <JSON> --out <フォルダ>`**: 指示は `{"title", "size", "slides": [部品の slides の 1 枚…],
   "pdf": [[PDF のパス, 何ページ目か], …]}`。PPTX は `pptx_writer.write` で、PDF は `pdfpages.assemble` で書く。
   PDF が読めない形なら PDF は書かずに rc=1（PPTX は書く）。指示が読めなければ rc=2
3. **PDF のページを抜いて並べる道具は自前の `scripts/pdfpages.py`**（標準ライブラリだけ・約 300 行）。読むのは
   Chrome（Skia）が印刷する形だけ: 相互参照は表・世代 0・ストリームの長さは数か数への参照。読めない形
   （PDF 1.5 の圧縮・暗号化など）は `PdfError` で止め、呼ぶ側は混ぜずに描き直した書き出しを使う
   - 選んだページから参照をたどれるオブジェクトだけを番号を付け直して写す。同じ元の字体などは 1 回だけ写す
   - 親から受け継ぐ属性（Resources・MediaBox・CropBox・Rotate）はページに写す。ほかのページへの参照（リンクの
     行き先）は null。文書の構造（タグ）は写さない
   - ストリームの中身はバイトのまま（描く中身は変えない。試験はページの中身のストリームが元と同じかを見る）

## 理由

- 版を切り替えたページ（Quick Slide の `_pin`）は、その版を描いた回の見た目のまま書き出したい。エンジンが変わった後に
  同じ台本で描き直すと、見た目が変わる（版を戻したのに別の絵になる）
- PDF は deck.html を Chrome で印刷したもの。回ごとに CSS が違うので、1 つの HTML にまとめて印刷し直すことはできない。
  回ごとの PDF からページを抜いて並べるのが確か

## 見送ったこと

- **pypdf を依存に足す**: 機体ごとに `pip --user` が要り、Homebrew の Python のように外から管理されている Python では
  導入の手順が増える（`quick_slide_setup.py` の 4 つのパッケージに 5 つ目を足すと、配った機体が全部やり直しになる）。
  使うのは「ページを抜いて並べる」だけで、読む PDF は自分で印刷したもの（形が決まっている）
- **pypdf を写して同梱する**: 配る物（このリポジトリ）に 2 MB の外のコードと許諾の文を抱え、更新を追う手間が残る
- **Chrome でページごとに印刷する**（`pageRanges`）: 分けることはできても、つなぐには結局 PDF を読む道具が要る。
  ページ数だけ印刷するので遅い
- ページごとに 1 ファイルの PDF に分けて残す: 字体の部分集合がページごとに重複し、混ぜた PDF が数倍に膨らむ
  （見本の 28 ページで 0.7 MB → 6.5 MB）。回の deck.pdf の何ページ目かを持てば足りる
